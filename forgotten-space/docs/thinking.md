任務規格、引擎實際行為與小說敘事尚未完全對齊。
1. 現有任務分類
分類	任務	目前定位
career/	fa_chain	法修循環歷練
career/	li_chain	力修循環歷練
career/	wu_chain	物修循環歷練

main/	rescue_maiden	戰鬥、搜查與劇情推進

這個結構已經能表達不同尺度的任務：職業日常、村莊主線、支線活動、長期史詩。沒有必要為了擴充而立刻推翻目錄分類。
但有一點值得注意：category、type、path_type 與 stages 是不同維度，未來應明確定義各自的語意，避免新任務增加後，逐漸依賴特殊的硬編碼判斷。
2. 優先修正的問題
P0 — 獎勵欄位沒有完整落實
cycle_of_craft、rescue_maiden、rescue_miners 的 JSON 使用 pot 設定潛能獎勵，但目前 handle_stage_completion() 沒有處理 pot。因此，照現有引擎實作，這些潛能獎勵不會依 JSON 定義發放。
village_pass 的 rewards.items 也沒有通用處理；雖然該任務目前另在步驟中發放路引，但這不代表通用獎勵欄位已被支援。
建議： 建立正式的獎勵處理器，明確支援經驗、金錢、潛能、天命、親和度、物品，並為每一種獎勵寫測試。



P0 — 任務啟動條件與進度條件需要嚴格驗證
JSON 中有 requirements.level、required_level、unlock_condition、target_type: "kill" 等設定，但不能假設引擎都會自動執行。
目前可見的 trigger_event() 有處理 talk、deliver、action，但在所檢查的事件分派分支中沒有看到對應的 kill 推進處理；等級需求也不能僅憑 JSON 欄位就視為已強制執行。
建議： 先確認所有事件的實際呼叫路徑，再建立統一的條件驗證層。未支援的欄位應在載入時報錯，而不是靜默忽略。



P1 — 部分行動任務沒有明確綁定地點
例如 fa_chain 的 wash、stargaze，以及其他任務中的 gather、strike。目前通用 action 推進主要比對動詞和可選目標，沒有在該分支統一驗證房間或區域。
如果呼叫端沒有額外限制，玩家便可能在不符合故事條件的地點完成步驟。
建議： 將地點、目標物件、裝備、物品數量與環境狀態納入任務條件；哪些條件必須由引擎驗證，應有明確規範。



P1 — 任務狀態與重複領取需要統一
quest_engine_d.c 已有階段、狀態和循環輪次，但 secure/quest_d.c 仍保留另一套任務資料與完成流程。cmd_quest.c 又會同時讀取兩套任務資訊。
這會增加重複顯示、獎勵差異、任務完成狀態不一致的風險。
建議： 確立單一權威任務來源，舊系統採相容層或逐步遷移，而不是讓兩套系統長期並行管理相同任務。



這些是從封裝內的程式碼與 JSON 得出的靜態檢查結果，不等於已經在執行中的 MUD 伺服器重現所有故障。特別是擊殺事件與地點限制，還需要繼續追蹤各指令的事件呼叫路徑，才能確認是否有其他層補上限制。
3. 任務合理性：幾個值得優先處理的具體案例
案例 A：wolf_hunter.json
需要核對事件路徑
任務要求擊殺 3 隻狼，再回報趙老獵。JSON 有 target_type: "kill" 與 required_count: 3，但目前可見的通用任務推進器沒有處理這種步驟的分支。
此外，舊版 secure/quest_d.c 也有一套擊殺進度邏輯，卻不代表新引擎會自動接收到該進度。
驗收條件： 擊殺非目標怪物不計數、同一死亡事件不重複計數、達到 3 隻後才能回報，而且完成獎勵只能領取一次。

案例 B：rescue_miners.json
物品條件尚未閉環
這條任務有很好的救援流程：取得線索、準備鋼鑿與辟煞用品、深入礦坑、聽取暗號、破石救人。
但 JSON 把 lost_item_recovery 寫在階段層級的陣列中，而目前 check_lost_item() 主要讀取當前步驟上的 lost_item_recovery。另外，對應鋼鑿、烈酒等物品也沒有在所有相關步驟上明確設為必需條件。
結果： 目前不能只憑這份 JSON，就認定物品遺失補領和救援裝備檢查都能正常運作。
建議將「必要裝備」「消耗品」「線索物件」分開處理。裝備應檢查是否持有或裝備；消耗品應在正確時機扣除；線索物件則不應因為玩家誤丟而永久卡死。

案例 C：ancient_order.json
適合保留的架構
三階段史詩任務從黑石鋪延伸至金石城，再到名山宗門；第一階段完成後進入 DORMANT，等待後續地圖和 NPC 條件解鎖。
這很適合你想做的長篇世界：玩家可以先取得殘缺信物，卻無法在新手村直接解開整個太古秘密。
不過，required_level、階段解鎖、信物驗證與最終獎勵都應由統一引擎強制執行。不能讓 JSON 看起來有規則，實際上卻只靠提示文字引導玩家。

案例 D：三大道統循環任務
有擴充價值
fa_chain、li_chain、wu_chain 都不是純粹的殺怪清單，而是透過觀星、追蹤、鍛造等活動建立修行方向。
尤其 wu_chain 把礦工、藥師與鐵匠串成一個生產閉環，最符合你想讓新手村成為活生生聚落的方向。
但要注意：type: "loop" 的循環任務必須能重複領取而不重複發放不該重複的關鍵道具，也不能讓玩家以同一個低成本動作無限刷取稀有資源。


三、我會怎樣調整整體架構
我不建議現在就大量新增任務，而是先讓既有任務形成可擴充的標準。
建議的任務處理流程
任務 JSON 定義
任務 ID、階段、條件、步驟、獎勵


載入與規格驗證
欄位型別、引用有效性、條件支援度、獎勵合法性


統一任務狀態機
前置條件 → 觸發 → 推進 → 階段解鎖 → 完成或循環


世界事件
環境變化、怪物狀態、地質危險、村民活動


玩家事件
對話、擊殺、採集、製作、探索、交付




統一條件判定與結算
地點、物品、技能、世界狀態、獎勵與持久化


這裡最重要的架構界線是：世界事件不等於玩家任務進度。
例如北崖礦坑穩定度下降，是世界狀態；玩家接到救援委託，是任務狀態；玩家破石成功，則是能同時影響世界與個人任務的事件。
未來若同一場礦難需要被小說、NPC、任務、環境危險和村民日常共同引用，就不應讓每個子系統各自製造一份互不相通的礦難狀態。
四、擴展性最重要的下一步
我建議先建立四份規格，而不是直接改寫所有 LPC。
規格	目的
任務 JSON Schema	定義所有合法欄位、型別、必填條件與版本
事件契約	統一 talk、kill、action、deliver 等事件的資料格式
狀態與獎勵契約	明確規定何時推進、如何防止重複結算，以及物品遺失怎麼處理
小說與 MUD 對照表	區分小說專屬事件、玩家可選奇遇、共用世界事件與永久世界變化
有了這四份規格，未來新增一個村莊、十條任務或一條跨區域史詩線，都不必重新修改整套引擎。

五、建議的實施順序
1. 第一階段：修正既有任務的實際行為。
   先處理獎勵欄位、等級條件、擊殺事件、地點限制、階段層級的遺失補領，以及兩套任務系統的權責問題。
2. 第二階段：讓黑石鋪成為可持續運作的聚落。
   把採集、鍛造、商隊、礦坑、獸群與村民生計連接到同一套世界狀態。任務應反映世界，而不是所有世界活動都只為任務服務。
3. 第三階段：建立稀有奇遇的獨立規則。
   將奇遇觸發條件、認知門檻、角色適配性、事件唯一性、失敗後果和線索持續性獨立建模。不要把奇遇直接等同於 fate +1 或發放一件遺物。
4. 第四階段：才擴充第四、第五象的正式設計。
   等前三條線和任務引擎已能表達「發現—共鳴—後果」之後，再決定柳清虛與沈泥各自真正不可替代的奇遇。如此可以避免先寫出精彩設定，最後卻只能用一般任務腳本勉強實現。
最後，我認為目前最值得保留的是兩個核心方向：小說的五種身世與生活環境各自引出不同的太古遺跡；MUD 的任務又試圖把日常生計、玩家成長與長期世界秘密串在一起。
接下來最有價值的工作，是先完成一次「小說—事件—任務 JSON—引擎」的四方一致性審核。 這會比單純再寫幾條任務，更直接地提高《被遺忘的空間》的可信度與長期擴充能力。
